# 主动发现、一次查证与工作接续

星舵可以自主发现值得推进的事项，向一个合适的 Agent 派一次只读查证，并在手机主聊天里主动汇报。用户同意把这件事交给星舵后，它才成为正式工作。手机始终面向同一个总控。

## 唤醒与判断

总控在 Mac 或其他自托管主机上沿用现有任务循环。每个进行中的目标可保存下次检查时间、原因、关注的事件以及最近处理的状态版本。用户指定的时点或周期优先。未指定时，星舵根据截止时间、依赖、最近进展选择检查时间。相关结果到达、设备重新在线或用户修改要求时，可以提前检查。普通心跳只刷新在线状态。没有目标或新证据时不调用模型。为防止频繁唤醒，合并同一状态版本的事件，对持续无变化的状态逐步拉长间隔。主机重启后每个到期事项只补看一次。

唤醒时先判断证据是否已经属于某件工作。如果有关联，按其最新目标、参与者、权限和任务回执推进。已有 Agent 在处理就等待；前置结果就绪才派下一步；齐备后交付并停止唤醒。“暂停”“取消”“忽略”和“等我继续”优先于定时器或回执。阶段暂停只约束该阶段。等待用户决定时，设备上线或模型建议都不能代替用户决定。

## 自主发现的事项

发现依据限于用户允许星舵观察的来源，如之前明确留下的目标、相关会话中可引用的新进展或尚待核对的依赖。排除已忽略、撤回、归档或要求遗忘的来源。空闲设备本身不能构成派单理由。相似标题只用于找候选，不能决定两件事属于同一工作。

已登记设备的活动元数据可用于本地发现。需要读取桌面正文时，使用用户已选择关联或明确要求关注的来源，并优先让有权读取该来源的本机 Agent 核对。设备可被索引不等于可以把正文转交其他机器或模型。跨端查证只发送用户已允许该接收方获取的最少材料。没有合适执行端时，在卡里说明缺什么依据。

先保存候选编号、来源、触发事实、要查的一个问题和状态。使用目标及可追溯的来源/事件去重，合并同一事项的设备回报、计时唤醒和措辞变化。候选编号仅用于查证、汇报和关联用户决定；此时不建立工作单、工作身份、桌面参与关系或总控会话。

去重以已记录的目标或依赖标识、可定位的资源和同一事实为依据。模型只能提议关联。来源不足以区分新事项与已经查过的事项时，先合并展示线索，自动查证额度保持原值。按目标保存发现游标；没有正式工作的已授权来源也可被新事件唤醒。等待回复期间只更新同一卡的证据。忽略覆盖该事项，直至用户明确重新提出。

确有待核对的事实时，选择一台已注册设备上有相关上下文且支持只读执行的 Agent。一个候选在所有设备和唤醒中合计至多一个自主查证任务。使用独立执行环境，输入只含查证所需的资料。由服务端固定只读模式并限制动作，不能写入用户工作区、转派、接力或创建产物。查证意图和固定请求编号先落盘，投递超时按原编号对账。新目标端、改写提示词或再次执行均算第二次。查证未成功、资料不足或互相矛盾也要如实汇报。现成证据充分时可以直接汇报。

若用户后来明确说“再查一次，先别立项”，把这一条用户消息作为单次只读委托记在原卡上，按用户请求编号去重。它不能恢复自主额度，不能创建工作，也不能授权后续连续派单。沉默或单纯查看结果都不会产生这个动作。

主聊天用同一张卡从“发现事项 / 只读查证”更新到结果，展示触发原因、设备、Agent、进度、耗时、证据和建议。结果到达主动通知一次。候选处于等待决定时不自行开工。用户忽略后，同一事项的旧证据、重复回执和重新上线不会再次触发它。

## 同意后沿用一件工作的身份

“同意立项”针对一张具体卡和卡上展示的目标、交付条件、建议的下一步。允许用户直接在主聊天明确同意；多个候选同时等待且一句“可以”没有明确指向时，只问指的是哪一项。设备回执、模型判断、点击查看或用户沉默都不是同意。发生实质范围变化时，须呈现新范围供用户决定。立项沿用用户同意的执行范围和既有权限。

卡片带候选编号和提案版本。服务器只接受来自已认证用户的决定。聊天中的肯定回复必须能关联到具体提案；被引用的 Agent 文本和由模型构造的消息不具备批准权。批准或忽略均以提案版本为条件写入，旧卡不能覆盖新决定。等待决定的候选可以随时被忽略；若查证尚在进行，则走原请求的撤回路径并吸收迟到回执。

批准时在单个本地事务内记录用户决定、候选与工作间的唯一关联、目标和验收条件，并把查证作为有来源的前期证据。新工作使用同一次用户批准消息作为工作根编号，沿用现有 `workId` 与关联回合的记录方式。即使此时尚无桌面会话，也能先建立工作根，随后按现有机制加入参与者。若已能证明对应同一工作，展示该关联供用户同意后归入原编号。并发同意或服务重启都返回同一编号；正式派单在提交后按现有队列请求编号投递。

归入已有工作时，事务还要核对用户看到的工作编号、范围版本和有效状态。仅有手机工作单的旧记录沿用最初工作单的根回合，补上接续映射。若用户同意前该工作已停止或范围已改，保留原卡等待更新后的决定。

每个参与者仍以设备、Agent 连接器、会话编号识别。子任务、用户的新要求、依据、交付物和停止回执均关联同一工作。查证用到某条桌面记录不等于把该会话登记为参与者；已关联原会话继续只接收工作摘要、只回执，用户在那里说“继续”才执行。总控在授权内主动推进时，沿用 Worker 派单通道。

## 方案选择与实现位置

在已有 `PersonalAgent.tick` 里检查持久化的唤醒计划，由状态变化和到期时间共同触发。现有定期复查继续服务“到时汇报”，扩展工作判断需要核对最新范围并能派单。新增独立的候选记录与单次查证入口。当前交互式 `consult` 会建立工作单，直接复用会提前立项；候选只复用底层只读队列、设备注册、消息与通知。正式工作复用工作单、修订、任务卡、核对交付与跨端接续。按每个候选开总控 session 会分散用户的单一对话；只按固定周期巡检则会错过刚解除的依赖。

## 验收

1. 使用虚构的展览筹备数据。两个设备回报同一目录缺少清单，定时器同时到期。总控只创建一个候选，主聊天仅出现一个只读任务。接受派单后丢失响应、重启再投递，执行端仍只接一单。
2. 查证后向手机汇报发现和来源。分别覆盖查证失败、证据不足、用户忽略、用户未回复。核对正式工作、桌面绑定及后续派单数都为零。
3. 模拟两张待决定的卡、一句含糊回复和两次针对同一卡的同意。只有明确同意使候选升级一次。先在手机立项，再关联两台设备上的不同 Agent 会话。手机、两端工作事件、任务卡与最终交付引用同一工作编号。
4. 手机要求暂停电子目录、纸本继续。设备上线和旧计时器同时到达，只推进纸本；读到两本纸书的有效证据后按新目标交付并停止唤醒。检查原桌面会话的自动回合只有收悉。
5. 覆盖没有新证据时的静默、发现通知去重、重启补看和工作中途修订。自动化测试记录派单及状态变化；真机另验主聊天卡片、通知及桌面原会话回执。
6. 仅可本机读取的来源不能随查证跨端转发。用一次明确的“再查一次，先别立项”验证用户手动委托和自主额度独立；复制回执或重放该消息均不会再次执行或立项。
